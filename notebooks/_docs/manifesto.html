2  FreeMPE

2.1 Mission

FreeMPE is a preservation and interoperability project for expressive electronic musical instruments.

Its purpose is to help musicians retain practical ownership of hardware they have legitimately purchased when essential functionality depends on proprietary configuration software, licensing infrastructure, cloud services, abandoned applications, or vendors that can no longer support their products.

The initial case study is ROLI hardware, especially:

  • 2 × Seaboard Blocks
  • 1 × Lightpad Block
  • 1 × LUMI Block

The project should eventually be useful to other MPE and expressive-MIDI devices.

The long-term aspiration is:

A musician should be able to buy an expressive controller, keep it for decades, and continue configuring and performing with it even if its manufacturer disappears.

FreeMPE should become both:

  1. standalone open-source tooling where missing tooling must be recreated; and
  2. a landing space for compatible open-source work that already exists elsewhere.

3 Governing principle

Preserve the instrument, not the vendor ecosystem.

A Seaboard is valuable because of its playing surface, sensors, firmware and expressive MIDI output.

It should not require continued existence of:

  • an account server,
  • a subscription,
  • a proprietary synth,
  • a proprietary installer,
  • a cloud configuration service,
  • or a particular company

to remain useful as an expressive musical instrument wherever technically avoidable.

MPE, MIDI, USB MIDI, Bluetooth MIDI and other public/interoperable standards are preferred boundaries.

4 Ethical boundary

FreeMPE exists for preservation, repair, interoperability, accessibility and continued use of legitimately owned hardware.

Prefer:

  • documented interfaces;
  • standard MIDI/MPE;
  • observation of one’s own devices;
  • clean-room protocol documentation;
  • user-owned configuration data;
  • legally obtained installers and firmware;
  • replacement configuration software;
  • open drivers;
  • reproducible tests;
  • compatibility layers.

Do not make software piracy the project’s organizing purpose.

Do not distribute proprietary firmware, commercial sound libraries, paid applications, license keys or copyrighted vendor code unless redistribution is clearly permitted.

If a proprietary application becomes unavailable, distinguish carefully between:

A. keeping purchased hardware interoperable

and

B. obtaining proprietary commercial software without authorization.

FreeMPE primarily solves A.

Where jurisdiction-specific reverse-engineering or circumvention law becomes relevant, document the uncertainty rather than pretending legal conclusions are universal.

5 Critical engineering rule

Never modify a working device merely to investigate it when observation will suffice.

Preservation comes before experimentation.

For every device:

  1. Establish a known-good baseline.
  2. Record firmware/version information.
  3. Archive legitimately available supporting software.
  4. Record current configuration.
  5. Verify ordinary MIDI/MPE behavior.
  6. Capture communication generated by official tools.
  7. Only then experiment with replacement tooling.

Do not flash experimental firmware while a userspace solution remains possible.

6 Current factual model

Treat all of the following as hypotheses to verify, not assumptions:

  • Basic note/expression output may survive independently because ROLI devices communicate using MIDI/MPE.
  • Some advanced configuration may depend on ROLI Dashboard.
  • Lightpad functionality may depend more heavily on downloaded apps/configuration than a Seaboard’s ordinary keyboard behavior.
  • LUMI may have a different configuration and firmware architecture from BLOCKS.
  • Firmware recovery/update procedures may contain server dependencies even where the resulting device operation is offline.
  • ROLI’s proprietary synth/software licensing is a separate preservation problem from keeping the controllers functioning as MPE hardware.

Maintain a table for every claim:

Claim Status Evidence Device Reproducible?
Device emits MIDI offline unknown/confirmed test/log/source model yes/no
MPE works offline … … … …
Configuration persists after reboot … … … …
Dashboard requires login … … … …
Configuration protocol understood … … … …

Never allow community rumor to silently become project fact.

7 The FreeMPE compatibility target

The minimum useful endpoint for each controller is:

POWER ON → CONNECT → EMIT STANDARD MIDI/MPE → PLAY

without contacting the manufacturer.

The next tier is:

CONFIGURE LOCALLY

including whatever the hardware exposes, such as:

  • MPE on/off
  • MIDI channel zones
  • pitch-bend range
  • velocity response
  • pressure response
  • glide/slide sensitivity
  • octave
  • scale/layout
  • LED state
  • Lightpad layouts
  • controller mappings

The aspirational tier is:

FULL OPEN CONTROL

where every useful configuration capability of the official configuration application has an open equivalent.

8 Project architecture

FreeMPE should be layered.

8.1 Layer 0 — Standards

Document the standard behavior underneath everything:

  • MIDI
  • MIDI 2.0 where relevant
  • MPE
  • USB MIDI
  • Bluetooth MIDI
  • SysEx
  • HID or vendor-specific USB interfaces where discovered

Do not reverse-engineer a proprietary mechanism if the desired behavior is already exposed through a standard interface.

8.2 Layer 1 — Observation

Tools for answering:

What is this device actually sending and receiving?

Produce reproducible captures of:

  • USB descriptors
  • MIDI messages
  • MPE channel behavior
  • SysEx traffic
  • BLE services where relevant
  • configuration changes
  • startup/shutdown behavior

Prefer passive capture before active probing.

8.3 Layer 2 — Protocol documentation

Translate observations into human-readable specifications.

Example conceptual record:

set_pitch_bend_range(value)

rather than merely:

F0 00 ... F7

Every discovered message should document:

  • direction
  • trigger
  • payload
  • expected response
  • device/model
  • firmware tested
  • persistence
  • confidence

8.4 Layer 3 — Open control library

Implement the protocol independently.

Conceptually:

freempe
    devices/
        seaboard_block
        lightpad_block
        lumi_block
    midi/
    mpe/
    transport/
    protocols/

The library should not require a GUI.

Everything important should eventually be callable programmatically.

8.5 Layer 4 — CLI

Example future interface:

freempe list

freempe inspect "Seaboard Block"

freempe mpe on

freempe bend-range 48

freempe sensitivity pressure 0.72

freempe lightpad layout chromatic

freempe backup device-backup.json

freempe restore device-backup.json

Syntax is illustrative until the protocol is understood.

The CLI becomes the reference implementation because it is:

  • inspectable;
  • scriptable;
  • testable;
  • portable;
  • easy to preserve.

8.6 Layer 5 — GUI

Only after the protocol/library is stable, provide an approachable open replacement for vendor configuration tools.

The GUI should call the same library as the CLI.

Do not bury device knowledge exclusively inside GUI code.

9 First preservation sprint

Before ambitious development, FreeMPE should produce a survival kit for the devices currently available.

For each of:

  • Seaboard Block #1
  • Seaboard Block #2
  • Lightpad Block
  • LUMI Block

record:

  • exact model/generation
  • serial number privately where useful
  • firmware version
  • battery condition
  • USB identifiers
  • Bluetooth identity
  • current MIDI behavior
  • current MPE behavior
  • settings exposed by official tools
  • which settings persist after power cycling
  • behavior with Internet disconnected

Archive locally, where legitimately obtainable:

  • official manuals
  • support articles
  • current installers
  • firmware files
  • release notes
  • SDK/API documentation
  • public developer documentation
  • public example code
  • license texts
  • MPE specifications

Record SHA-256 hashes for archived binaries so later researchers can identify exact versions.

Do not publish vendor binaries merely because they were archived privately.

10 The crucial experiment

The initial research question is not:

How do we jailbreak a ROLI?

It is:

How much of a ROLI already belongs to the musician without ROLI’s infrastructure?

Build an offline test environment.

Disable network access.

Connect one device.

Determine:

  1. Does the OS recognize it?
  2. Does it send MIDI?
  3. Does it send valid MPE?
  4. Can an independent MPE synth play it?
  5. Does its last configuration survive?
  6. Which functionality is actually missing?
  7. What does Dashboard add?
  8. Does Dashboard itself still function offline?

Repeat separately for each device class.

The result should be a dependency map, not a binary statement that the device is either “free” or “bricked.”

11 Protocol-discovery workflow

When official Dashboard changes a setting:

  1. Record device state before.
  2. Start appropriate USB/MIDI/BLE capture.
  3. Change exactly one setting.
  4. Stop capture.
  5. Record device state after.
  6. Repeat the same change.
  7. Reverse the change.
  8. Compare messages.
  9. Test the suspected message independently.
  10. Document confidence.

Change one variable at a time.

Examples:

  • pitch-bend range 24 → 48
  • MPE off → on
  • pressure sensitivity low → high
  • octave 0 → +1

This converts the official application into a temporary protocol oracle while it still exists.

That may be FreeMPE’s most time-sensitive activity.

Raw captures should be preserved whenever legally shareable, together with:

  • operating system

  • firmware version
  • transport
  • exact action performed

A protocol claim without reproduction metadata is provisional.

13 Community design

FreeMPE should eventually allow other owners to contribute evidence without needing to become reverse engineers.

Useful contribution templates:

13.0.1 Device report

  • device
  • generation
  • firmware
  • OS
  • works offline?
  • MPE works?
  • configuration software works?
  • observed failure

13.0.2 Protocol experiment

  • device
  • firmware
  • official application
  • setting changed
  • before
  • after
  • attached capture
  • interpretation

13.0.3 Preservation report

  • artifact name
  • version
  • original source
  • hash
  • redistribution license/status

This lets many owners collectively reconstruct an ecosystem from independent observations.

14 Definition of “free”

Do not use “free” to mean merely zero cost.

A device becomes progressively freer when the musician can:

  1. connect it without vendor authentication;
  2. play it using open standards;
  3. configure it without vendor servers;
  4. back up its state;
  5. restore its state;
  6. update/recover it locally;
  7. understand its protocol;
  8. replace proprietary utilities with open ones;
  9. migrate between operating systems;
  10. keep using it after the original manufacturer disappears.

Track these independently.

A device can be playable but not configurable, configurable but not recoverable, or recoverable but dependent on proprietary firmware.

That nuance matters.

15 Product philosophy

FreeMPE should make hardware ownership durable.

It should not attempt to become another ecosystem that musicians become dependent upon.

Therefore:

  • use open formats;
  • document protocols;
  • make state exportable;
  • avoid mandatory accounts;
  • avoid mandatory cloud services;
  • keep core functionality offline;
  • make APIs stable and documented;
  • ensure the software can itself be forked and preserved.

FreeMPE must be able to survive the disappearance of FreeMPE.

16 Relationship to musical practice

This project exists because expressive controllers are instruments.

The software should disappear behind musicianship.

For the current performance project, the desired boundary is:

PHYSICAL GESTURE
      ↓
Seaboard / Lightpad / LUMI
      ↓
standard MIDI / MPE
      ↓
iPad / AUM / AUv3 / future host
      ↓
MUSIC

ROLI-specific infrastructure should terminate as close to the hardware as possible.

A future show-control system should understand semantic roles such as:

  • expressive keyboard
  • pressure
  • glide
  • timbre
  • XY control
  • trigger surface

rather than requiring a particular ROLI product.

This makes eventual hardware replacement possible without redesigning the musical instrument.

17 ChatGPT/Codex operating instructions

When working inside this Project:

Research before modifying.

For every technical question:

  1. identify the exact device and firmware;
  2. inspect available official documentation;
  3. inspect existing OSS work;
  4. establish current supported behavior;
  5. reproduce it;
  6. only then propose reverse engineering or replacement code.

Do not begin by inventing wrappers.

Prefer the simplest standards-compliant explanation first.

When investigating protocols, separate:

  • observed fact;
  • vendor documentation;
  • community report;
  • hypothesis;
  • verified implementation.

Never describe a hypothesis as a protocol fact.

When writing code:

  • make experiments small;
  • log raw inputs/outputs;
  • preserve fixtures;
  • add regression tests once behavior is understood;
  • avoid irreversible device operations;
  • keep vendor-specific code isolated;
  • prefer cross-platform libraries.

When a discovery is made, ask:

Can this become documentation or a reproducible test so another musician never has to rediscover it?

If yes, produce that artifact.

18 Initial milestones

18.1 M0 — Freeze the lifeboats

Archive legitimate documentation, installers, firmware and version information while available.

No reverse engineering required.

18.2 M1 — Offline survival matrix

For all four current ROLI devices, establish exactly what works with:

Internet disconnected.

Produce the compatibility matrix.

18.3 M2 — MPE independence

Demonstrate each suitable controller driving at least one non-ROLI MPE instrument without proprietary synthesis software.

18.4 M3 — Configuration dependency map

Identify every setting that presently requires Dashboard or another ROLI application.

18.5 M4 — First open configuration

Choose one harmless configuration parameter.

Observe official behavior.

Reproduce it independently.

Document it.

This is the first true FreeMPE milestone.

18.6 M5 — Read-only inspector

Create:

freempe inspect

that can identify supported connected devices and report everything safely observable.

18.7 M6 — Minimal open dashboard

Configure the handful of parameters necessary for ordinary MPE performance without ROLI software.

18.8 M7 — Preservation community

Publish protocol documentation, compatibility information, contribution procedures and carefully licensed OSS tooling.

Then expand beyond ROLI.

19 North-star demo

The project succeeds when we can take a freshly installed computer with:

  • no ROLI account;
  • no ROLI cloud access;
  • no ROLI software;

connect a legitimately owned Seaboard Block and run something equivalent to:

$ freempe inspect
Seaboard Block detected
Firmware: ...
Transport: USB
MPE: enabled
Pitch bend: 48 semitones

$ freempe configure mpe --bend-range 48
Configuration applied.

Then open an independent MPE synth and play.

No vendor server participated.

At that moment the musician—not a defunct account system—owns the practical future of the instrument.

20 Immediate next task

Do not write FreeMPE yet.

Start with the four devices physically available.

Create the ROLI Survival Matrix and perform the offline-baseline experiments.

The first question FreeMPE must answer empirically is:

If ROLI’s servers disappeared tonight, exactly what would stop working tomorrow?
